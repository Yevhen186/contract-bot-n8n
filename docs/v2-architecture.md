# Contract Bot v2.0 — архитектура

Статус: черновик для обсуждения (2026-10-31). В n8n ничего не внедрено.

## 1. Что меняется по сути

v1: каждое сообщение сразу распознаётся, шаг сессии решает, каким парсером.
v2: сообщения только **копятся** (как сырой текст), распознавание — **один раз** по кнопке «✅ Готово» по всей пачке.

```
/start → компания → тип договору (З / П / Обидва)
   → step=collecting
   → любые сообщения/файлы → Normalize Text (как в v1) → строка в листе Inputs → «📥 Прийнято (N)»
   → «✅ Готово»
   → Extract All (1 вызов GPT-4.1-mini по всей пачке)
   → Post-process (код: SHORT-поля, проверки IBAN/ЄДРПОУ, бизнес-правила)
   → step=review → экран подтверждения
        ├─ голос/текст «зміни/додай …» → Patch (GPT поверх текущих данных) → новый экран
        ├─ «🚀 Генерувати» → step=generating → sub-workflow Generate (1 или 2 договора) → step=done
        └─ «❌ Скасувати» → сброс
```

## 2. Хранение

### Sessions (существующий лист) — колонки
A chat_id | B step | C company | D role | E data | F updated_at | G raw_input (не используется) | **H batch_id** (новая)

- `data` — JSON всех извлечённых полей (после Extract/Patch).
- `batch_id` — метка текущей пачки (`Date.now()` при выборе роли). Нужна, чтобы отделить входы этого договора от прошлых, ничего не удаляя.
- steps: `""` → `choose_company` → `choose_role` → `collecting` → `review` → `generating` → `done`.
- roles: `automov_z`, `automov_p`, `automov_both`, `uts_z`, `uts_p`, `uts_both`.

### Inputs (новый лист в той же таблице)
chat_id | batch_id | kind | name | text | created_at

**Почему отдельный лист, а не raw_input:**
1. Альбом из 5 фото Telegram шлёт как 5 отдельных апдейтов → 5 параллельных запусков n8n. Схема «прочитал ячейку → дописал → записал» теряет данные при параллельных запусках. Append новой строки — не теряет.
2. Лимит ячейки Google Sheets — 50 000 символов. Один PDF-договор легко даёт 20–30 тыс.
3. Видно в таблице, что именно бот «услышал» с каждого файла — удобная диагностика.

## 3. Приём входов (step=collecting)

Ветка медиа v1 (Whisper / Vision / PDF / Word → Normalize Text) **переиспользуется без изменений**, кроме:
- промпт Analyze PDF делается универсальным (не только реквизиты, а «выпиши весь текст документа как есть»);
- после Normalize Text вместо парсеров: **Append to Inputs** → ответ «📥 Прийнято (3): PDF "Виписка.pdf". Надсилайте ще або натисніть ✅ Готово».
- Если текст пустой (распознавание не удалось) — не сохраняем, пишем «⚠️ Не вдалося прочитати файл».

Кнопки — **постоянная reply-клавиатура** (внизу экрана): `✅ Готово` / `❌ Скасувати`. Нажатие = обычное текстовое сообщение, поэтому ловится простым IF по тексту, без callback-ветки. (Пункт «Persistent reply keyboard» уже есть в README → What's Next.)

Риск: пользователь жмёт «Готово», пока PDF ещё обрабатывается (10–20 с) → этот PDF не попадёт в пачку. Решение: в «Готово» пишем, сколько входов взято («Беру 4 документи»), а подсказка после каждого входа: «натискайте Готово після підтвердження всіх файлів».

## 4. Extract All

Code «Build Bundle»: Get Inputs (chat_id + batch_id) → склейка:
```
=== Документ 1 (pdf: Виписка.pdf) ===
...текст...
=== Документ 2 (voice) ===
...
```
Объём: GPT-4.1-mini держит ~1 млн токенов, типичная пачка 5–30 тыс. Ограничим 300 000 символов с предупреждением.

HTTP Request → GPT-4.1-mini, temperature 0, json_schema strict. Схема **одна на все роли**:
- все поля Замовника, Перевізника, Рейса (плоские строки, как в v1);
- `conflicts`: массив `{field, options[]}` — если в разных документах разные значения одного поля;
- `unassigned`: массив `{name, edrpou}` — компании, сторону которых нельзя определить;
- `notes`: строка — что модель считает важным, но не легло в поля.

### Как модель отличает стороны
В system-промпт (из Code-ноды конфигурации) подставляется:
1. **Наши реквизиты** (АвтоМув / ЮТС) — «это экспедитор, НИКОГДА не записывай его в CLIENT_* или CARRIER_*». Без этого заявка от клиента, где есть обе стороны, перепутается чаще всего.
2. Тип договора: для `_z` все чужие компании по умолчанию = Замовник; для `_p` = Перевізник; для `_both` — по меткам «Замовник/Перевізник», по признакам (кто платит / чей авто и водитель), иначе → `unassigned`.
3. Правила из промптов v1 (форматы ФОП/ТОВ, IBAN без UA, ПІБ полностью и т.д.) — переносим как есть.

`unassigned` на экране подтверждения превращается в вопрос с кнопками: «ТОВ "Альфа" (12345678) — це: [Замовник] [Перевізник]».

## 5. Post-process (Code, без LLM — детерминированно)

- `*_COMPANY_SHORT`, `*_DIRECTOR_SHORT` (одна функция вместо трёх копий);
- IBAN: убрать пробелы и `UA`; проверить 27 цифр + **контрольную сумму mod-97** → ловит ошибки OCR в цифрах;
- ЄДРПОУ: 8 цифр (ТОВ/ПП) или 10 (ФОП); **контрольная цифра ЄДРПОУ** для 8-значных; для ФОП IPN = EDRPOU;
- ЮТС + международный маршрут → предупреждение (ЮТС только внутренние);
- внутренний рейс → CUSTOMS_LOADING / BORDER_POINT / CUSTOMS_UNLOADING = пусто;
- CARGO_VALUE оставляем только для automov_p;
- CONTRACT_NUMBER, CONTRACT_DATE, TRANSPORT_TYPE — как в v1;
- итог: `data`, `missing[]`, `warnings[]` по списку полей **конкретного шаблона** (карта «роль → нужные плейсхолдеры» в Code-ноде Template Config).

Автоскан плейсхолдеров из шаблона: возможно (Docs API + regex), но шаблонов 4 и меняются редко — не окупается сейчас. Карта в одной Code-ноде даёт тот же эффект: новый шаблон = одна запись в конфиге.

## 6. Экран подтверждения (step=review)

Одно сообщение, без parse mode, код гарантирует < 4096 символов (длинные значения обрезаются до ~70 символов):
```
📋 АвтоМув → Замовник. Знайдено 26 з 31

ЗАМОВНИК
Назва: ТОВ "Альфа"
ЄДРПОУ: 12345678   IBAN: …4567 ✅
Директор: Іваненко Іван Іванович
…
РЕЙС
Маршрут: м. Київ - м. Варшава
Завантаження: 03.11.2026, м. Київ, вул. …
…
❗ Не знайдено: Email замовника, Дата доставки, Водій
⚠️ Різні значення: IBAN (2 варіанти) — уточніть
⚠️ IBAN перевізника не пройшов перевірку контрольної суми

Надішліть голосом або текстом, що змінити / додати.
```
Inline-кнопки: `🚀 Генерувати` `❌ Скасувати`.

Дозаполнение: любое сообщение на шаге review (текст/голос/фото) → Normalize Text → **Patch**: тот же GPT-вызов и та же схема, но на вход «поточні дані (JSON) + нове повідомлення; зміни тільки те, що просить користувач» → Post-process → новый экран. Новое фото/PDF на этом шаге тоже работает как дополнение.

## 7. Генерация — sub-workflow «Contract Generate»

Цепочка v1 Copy file → Convert → Build Replace → Replace → Export → Send → Delete выносится в отдельный workflow с входом `{chat_id, role, data}` и вызывается нодой **Execute Workflow** (по одному разу на каждый item).

Почему: для «Обидва» нужно 2 договора. Внутри одного workflow цепочка с `$('Get Session').item` на 2 item'ах — риск перепутать pairing (связь items). Sub-workflow запускается чисто на каждый договор, плюс главный workflow становится короче.

«Обидва»: Code формирует 2 item'а — `automov_z` и `automov_p` (или `uts_*`) с одним и тем же `data` → 2 вызова → 2 .docx. Номер договора: один базовый + суффиксы `-З` / `-П` (решить).

Защита от двойного нажатия: «Генерувати» сначала ставит `step=generating`; повторное нажатие на этом шаге игнорируется.

## 8. Ошибки v1, которые закрываются

- Is Step Done `=={{` → исправлено.
- Error Handler Notify User — chat_id захардкожен → брать из Extract chat_id.
- Сбрасывать сессию явной записью всех колонок (урок 3), не полагаясь на поведение Append or Update.

## 9. Миграция и откат

v2 собирается как **копия** workflow («Contract Bot v2»). Один бот = один webhook, поэтому активен только один. Откат = выключить v2, включить v1 (JSON v1 лежит в git).

## 10. Стоимость (оценка, проверить по факту)

GPT-4.1-mini: пачка ~20k токенов вход + ~2k выход ≈ $0.01. Vision/PDF на gpt-4o ≈ $0.01–0.03 за файл. Итого договор ≈ $0.03–0.10.

## 11. Тестирование

- Локальный n8n при блэкаутах бессмысленен: без света нет ни ноутбука, ни туннеля, а Railway работает независимо → **берём Railway на месяц**, когда всё готово.
- До включения: Code-ноды (Build Bundle, Post-process, Review Screen) прогоняются локально на тестовых данных (Node.js), промпт Extract — можно прогнать скриптом на своих реальных документах.
- Живые тесты в Telegram: 1) happy path З; 2) П; 3) Обидва; 4) Patch голосом; 5) конфликты/битый IBAN; 6) альбом фото; 7) Скасувати и /start на каждом шаге.
